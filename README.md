# yong_ml — 적합성 평가·우선순위 평가·지역 유형·AI 추천 카드

Python으로 미리 계산해서 MariaDB `yongin`의 `ml_` 테이블로 저장해요. Spring은 이 표를 읽기만 하면 돼요.
입력은 `yong` 프로젝트가 만든 `feat_` 테이블과 민원 테이블이에요.

## 처음 세팅
Python 3.10 이상 (로컬 개발은 3.14).
```bash
git clone <저장소 주소> yong_ml
cd yong_ml
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```
`.env`에 값을 채우세요: `DB_USER`, `DB_PASSWORD`(yong 프로젝트와 같음), LLM을 쓰려면 `LLM_API_KEY`.
- `.env`는 깃에 올라가지 않아요. 서버에서는 `.env.example`을 보고 서버에 직접 만들어 주세요.
- 서버(Spring 등)에서 실행할 때는 `run_all.py` 맨 위 기본값에 기대지 말고 `--year`, `--month`를 항상 넘겨 주세요.
- LLM은 기본이 Gemini 무료 등급(`gemini-3.5-flash-lite`)이에요. 키는 Google AI Studio의 Get API key에서 받아요.
- 무료 등급 한도(분당·하루)가 있어서 분당 `LLM_RPM`(기본 10)번만 불러요. 한 기간(연간 또는 한 달) 카드 110개 ≈ 130회 ≈ 13분이에요.
- **연간 + 12개월 카드를 전부 LLM으로 만들면 약 1,700회**라 무료 하루 한도(500회)로는 4일쯤 걸려요. 한 번에 다 못 해도 괜찮아요: 한도가 차면 나머지는 템플릿 문장으로 저장되고, 다음 날 같은 명령을 다시 돌리면 이미 만든 LLM 카드는 그대로 두고 남은 것만 채워요.
- 분당 한도에 걸리면 기다렸다 다시 부르고, 하루 한도를 다 쓰면 그 실행의 나머지 지역은 템플릿 문장으로 만들어요.
- 무료 등급은 보낸 내용이 Google 제품 개선에 쓰일 수 있어요. 보내는 건 공공데이터 숫자와 민원 건수뿐이에요(민원 내용 X).

## 실행
먼저 yong 프로젝트의 `pipeline/run_all.py`가 같은 연도로 한 번 돌아 있어야 해요.

`run_all.py` 맨 위 두 줄만 바꾸고 실행하면 돼요.
```python
YEAR = "2025"     # 기준연도
MONTH = ""        # "" = 연간만 / "03" = 3월만 / "all" = 연간 + 1~12월 전부
```
**저장은 실행한 기간만이에요.** 미리 저장해 둔 다른 기간은 그대로 둬요. (예: 2025년 2월이 저장돼 있을 때)
1. `MONTH = ""` → 2025 연간이 추가돼요. 2월은 그대로예요.
2. `MONTH = "02"` → 2025년 2월이 덮어써져요. LLM 카드는 데이터가 그대로면 다시 안 만들어요.
3. `MONTH = "09"` → 2025년 9월이 추가돼요.
- 월별 점수는 어느 달을 저장하든 그 해 12개월을 같이 놓고 계산해서, 따로 돌려도 한꺼번에 돌려도 값이 같아요.
```bash
python run_all.py                  # 위 YEAR·MONTH 로 계산 → outputs/<연도>/*.csv + DB ml_ 테이블
python run_all.py --year 2026 --month 03   # 이번만 다른 연·월로
python run_all.py --no-llm         # LLM 안 부름 (저장된 LLM 카드는 그대로, 없는 카드는 템플릿 문장)
python run_all.py --llm-scope mvp  # LLM 문장은 백암·원삼만 (나머지 지역은 템플릿 문장, 카드는 모든 지역)
python run_all.py --fill-template  # 카드(ml_explanation)만 저장: 템플릿이거나 아직 없는 카드만 LLM 으로 채움
python run_all.py --regen-llm      # 저장된 LLM 카드도 전부 새로 (프롬프트를 바꿨을 때)
```
- **이미 만든 LLM 카드는 다시 만들지 않아요.** 같은 연·월 카드가 LLM으로 저장돼 있고 넘기는 사실·추천 결과가 그대로면 그대로 써요. 데이터가 바뀐 지역, 템플릿이던 지역, 처음 만드는 달만 LLM을 불러요.
- LLM 서버가 잠깐 과부하(503 등)이면 10초 → 30초 → 60초 기다렸다 다시 불러요(`config.LLM_RETRY_WAITS`). 그래도 안 되면 그 지역만 템플릿 문장이 돼요.
- 템플릿으로 남은 카드는 같은 명령을 다시 돌리거나 `--fill-template`(카드만 저장)로 채우면 돼요.
VS Code ▷ 버튼으로 `run_all.py`를 실행해도 `.venv`로 자동 실행돼요.

### 연·월 컬럼과 쌓기
- 모든 표가 같은 이름을 써요. **`ml_` 표는 전부 `year` + `month`** (연간 행은 `month`가 빈 값(NULL), 월별 행은 1~12).
  - 예) `year = 2025, month IS NULL`(연간) / `year = 2025, month = 5`. `month`는 숫자(1~12)라 화면에서 `05`로 보이게 하려면 표시할 때 두 자리로 바꿔 주세요.
  - `ml_model_info`는 실행한 기간마다 그때 모델 정확도가 들어가요 (모델은 연간 데이터로 학습).
- 입력: `feat_` 표에서 그 `year` 행만 골라 읽어요.
- 출력: 지우고 새로 만드는 게 아니라 **추가**예요. 이번에 실행한 `year`·`month` 행만 바꿔 넣고 다른 연도·달·연간은 그대로 둬요. 같은 연·월을 다시 돌려도 중복되지 않아요.
- Spring 에서 읽을 때는 `WHERE year = 2025 AND month IS NULL`(연간) 또는 `AND month = 5`(월별)처럼 꼭 걸어 주세요.

## 실행 API (Spring 연동)
`run_all.py`를 HTTP로 실행하는 엔드포인트 하나예요. 결과 값은 Spring이 DB(`ml_` 테이블)에서 직접 읽어요.
```bash
uvicorn api:app --host 127.0.0.1 --port 8000
```
| 요청 | 같은 명령 |
|---|---|
| `POST /api/ml/run` `{"year": 2025, "month": 1}` | `python run_all.py --year 2025 --month 01` |
| `POST /api/ml/run` `{"year": 2025}` | `python run_all.py --year 2025 --month ""` (연간) |

- 끝날 때까지 기다렸다가 응답해요: 200 성공, 409 다른 실행 중, 500 실패, 422 입력 형식 오류.
- 한 달 실행은 LLM 카드 포함 약 13분이라 Spring 쪽 읽기 타임아웃을 넉넉히(예: 30분) 주세요. 요청이 먼저 끊겨도 실행은 끝까지 가고 DB에 저장돼요.
- 인증이 없으니 외부에 열지 말고 같은 서버(127.0.0.1)나 내부망에서만 띄우세요.

## 실패할 때
- 로그 파일도, 화면 출력도 없어요. 결과는 종료 코드로 알려줘요.

| 종료 코드 | 뜻 |
|---|---|
| 0 | 성공 |
| 1 | 실패 |
| 2 | 다른 실행이 이미 돌고 있음. 아무것도 안 하고 바로 끝나요 |
| 130 | 사용자가 멈춤 |

- **한 번에 하나만 돌아요.** 시작할 때 MariaDB `GET_LOCK('yong_ml')`로 잠가요. 연도·달이 달라도 동시에는 안 돌아요 (`all`과 `01`이 겹치거나, LLM 분당 한도를 나눠 쓰는 걸 막으려고).
- 잠금은 실행이 끝나면 풀리고, 중간에 프로세스가 죽어도 DB 연결이 끊기면서 저절로 풀려요.
- Spring에서 실행할 때는 종료 코드 2를 받으면 `409 Conflict`(이미 실행 중)로 돌려주면 돼요.

## 입력 (yongin DB)
| 테이블 | 쓰는 곳 |
|---|---|
| `feat_village` | 리 72개 (처인구 읍면) — 행복택시 학습, 리 단위 점수, 지역 유형 |
| `feat_region` | 행정동 38개 — 동 단위 점수, 지역 유형 |
| `feat_stop` | 정류장 — 노선버스 효율·공급 모델 학습 |
| `feat_village_month` / `feat_region_month` | 월별 점수 (기준연도 1~12월). 택시 호출(월평균 → 지표 신뢰도)도 여기서 |
| `feat_region_hour` | 평일 시간대별 생활인구 → 출퇴근 비중 (노선버스 점수, 출퇴근 혼잡형) |
| `feat_city` / `feat_city_month` | 시 평균 (그래프와 같은 숫자로 비교하려고 고령 비율·택시 호출 성사율 평균을 여기서) |
| `app_complaint` | 민원 (지금은 더미). `.env`의 `COMPLAINT_TABLE`로 바꿀 수 있음 |

## 출력 (yongin DB, `outputs/`에도 CSV)
| 테이블 | 연·월 | 화면 | 컬럼 |
|---|---|---|---|
| `ml_priority` | year + month | 대시보드 지도·TOP 10·취약지역 수, 우선순위 | `unit`, `region_cd`, `region_nm`, `gu`, `score_mismatch`·`score_access`·`score_service`·`score_vulnerable`·`score_complaint`·`score_demand`·`score_feasibility`(0~100), `score_total`, `rank_total`, `is_vulnerable` |
| `ml_suitability` | year + month | 적합성 점수 | `unit`, `region_cd`, `mode`, `score`(0~100), `is_best`, `is_current` |
| `ml_region` | year + month | 상세 '지역 유형' 카드, 표본 부족 경고 | `unit`, `region_cd`, `type_nm`, `type_desc`, `type_chips`(JSON), `low_reliability`, `reliability_note` |
| `ml_explanation` | year + month | 상세 'AI 추천 해결방안', 대시보드 미리보기 | `unit`, `region_cd`, `is_keep`, `options`(JSON), `reasons`(JSON), `cautions`(JSON), `summary`, `source`, `created_at`, `context` |
| `ml_model_info` | year + month | (발표·확인용) | `model`, `target`, `n`, `metrics`(JSON), `trained_at` |

공통 키: `unit`(village / dong), `region_cd`(리 코드 또는 행정동 코드), `mode`(BUS / DRT / HAPPY_TAXI).
지역 이름은 `ml_priority.region_nm`에 있어요(리는 "백암면 용천리"처럼 면 이름 포함).

### 대시보드
- **지도 보기 토글**: 종합 = `score_total`, 교통 수요 = `score_demand`, 공급 부족도 = `score_service`
- **교통 취약지역 N개**: `is_vulnerable = 1` 개수 (`score_total` 50점 이상, `config.VULNERABLE_SCORE`). 2025 연간: 행정동 9곳, 리 13곳
- **TOP 10**: `rank_total` 1~10, `region_nm`, `score_total`
- **지역 미리보기**: 추천 대안 조합 = `ml_explanation.options`에서 `status = "추천"`인 칸의 `name` (현행 유지 지역은 '현행 유지' 하나), 추천 근거 요약 = `ml_explanation.summary`
- 화면에서 가중치를 바꾸면 Spring이 `score_*` 7개를 가중합해서 다시 정렬하면 돼요. `score_total`은 기본 가중치(30/20/20/10/10/5/5)로 낸 값이에요.

### 상세 — 시 평균과 비교 / 미배차율 추이 그래프 (yong 전처리 표를 그대로 읽음)
| 그래프 | 지표 | 이 지역 | 시 평균 | 단위 |
|---|---|---|---|---|
| 시 평균과 비교 | 버스 정류장 수 | `feat_region.n_stops` / `feat_village.n_stops` | `feat_city.n_stops` | **연간** |
| 시 평균과 비교 | 고령인구 비율 | `feat_region.ratio65` / `feat_village.ratio70` | `feat_city.elderly_ratio` | **연간** |
| 시 평균과 비교 | 택시 호출 성사율 | `feat_region_month.taxi_match_rate` | `feat_city_month.taxi_match_rate` | **월별** |
| 시 평균과 비교 | 생활인구 | `feat_region_month.fp_avg` | `feat_city_month.fp_avg` | **월별** |
| 미배차율 추이 | 택시 미배차율 | `feat_region_month.taxi_unmatched_rate` | `feat_city_month.taxi_unmatched_rate` | **월별** (2025년 1~12월) |

`feat_city`는 `unit`(dong / village)별 1행이에요. 리 화면은 `unit = village` 행(읍면 마을 평균, 70세 이상)을 쓰세요.
택시·생활인구는 행정동 단위 데이터라 리 화면에는 그 면의 값이 나와요.
`fp_avg`는 하루 이동 인원이 아니라 **그 시간에 머무는 사람 수의 시간 평균**이에요. 화면 이름은 "생활인구 (시간 평균)"을 권장해요.

### 상세 — 지역 유형 (`ml_region`)
6개 고정. 유형마다 정해진 지표의 백분위(그 유형 쪽 방향)를 평균해서 가장 높은 유형, 60 미만이면 '대중교통 양호형'.

| 유형 | 설명 (`type_desc`) | 보는 지표 |
|---|---|---|
| 외곽 대중교통 공백형 | 정류장과 버스가 모두 적고 거점까지 먼 외곽 지역이에요 | 정류장 밀도↓, 운행↓, 거점까지 시간↑, 인구밀도↓ (행정동은 읍면만) |
| 버스 운행 부족형 | 정류장은 있지만 버스가 드물게 다니는 지역이에요 | 운행↓, 대기↑, 하루 5회 이하 정류장 비율↑ |
| 정류장 접근 취약형 | 버스는 다니지만 정류장까지 멀어 걷기 힘든 지역이에요 | 정류장까지 도보↑, 500m 안 면적↓ |
| 고령 이동 취약형 | 어르신이 많은데 정류장까지 가기 어려운 지역이에요 | 고령 비율↑(동 65세+·장애인, 리 70세+), 도보↑ |
| 출퇴근 혼잡형 | 사람이 많아 출퇴근 시간에 버스가 붐비는 지역이에요 | 1회당 승차↑, 출퇴근 시간 생활인구↑, 인구밀도↑ |
| 대중교통 양호형 | 뚜렷한 공백이 없는 지역이에요 | (위 유형이 모두 60 미만) |

- 공백·부족·접근·고령 유형은 접근성·서비스 전체가 중간보다 나쁜 곳만 돼요(좋은 곳이 '공백형'으로 나오지 않게).
- 2025: 행정동 외곽 3 / 운행 부족 5 / 접근 6 / 고령 3 / 혼잡 12 / 양호 9, 리 7 / 13 / 11 / 5 / 15 / 21.
- `type_chips`: JSON 문자열 배열, 1~3개. 예) `["정류장 밀도 적음 · 1.9곳/km² (평균 3.4곳/km²)"]`
- **지표 신뢰도 (표본 부족)**: 행정동은 월평균 택시 호출 100건 미만, 리는 그 면의 월평균 택시 호출 100건 미만이거나 인구 300명 미만이면 `low_reliability = 1`, `reliability_note`에 화면 경고 한 줄. 기준은 `config.RELIABILITY_MIN_CALLS`, `RELIABILITY_MIN_POP`.
  2025: 리 7곳(인구 2~279명), 행정동 0곳(가장 적은 상현1동도 월평균 308건).
  예) "이 마을은 인구가 208명으로 적어 비율 지표의 신뢰도가 낮아요. 결과는 참고용으로만 봐 주세요."

### 상세 — AI 추천 해결방안 (`ml_explanation`)
**카드 수: 현행 유지 지역은 4개, 나머지는 3개**
- 현행 유지 = 지역 유형이 '대중교통 양호형'(뚜렷한 공백·혼잡 없음)이고 교통 취약지역(`is_vulnerable`)이 아닌 곳. 2025: 리 21곳, 행정동 9곳
- 현행 유지 지역: 맨 앞 '현행 유지' 카드(`mode = "KEEP"`)가 추천 1, 노선버스·똑버스·행복택시는 모두 '이번엔 제외'
  - 현행 유지 카드의 이유·근거 지표 = 그 지역이 평균보다 나은 접근성·서비스 지표 (`ml_region.type_chips`와 같은 사실)
  - 제외된 수단 이유: 운영 중이면 "지금 운영 중인 ○○로 충분해 따로 늘리지 않아도 돼요", 아니면 "새로 도입할 필요가 크지 않아요"
  - 주의사항에 "다시 검토한다면 ○○이 가장 가까운 대안이에요" (점수 1위 수단)
- 나머지 지역: 지금처럼 노선버스·똑버스·행복택시 3개 (추천 1~2개 + 제외)
- 끄려면 `config.KEEP_CURRENT = False` (모든 지역 3개)

| 컬럼 | 내용 |
|---|---|
| `is_keep` | 현행 유지 지역이면 1 (카드 4개). '현행 유지 N곳' 같은 집계는 이걸로 |
| `options` | JSON 배열, 카드 순서대로 (아래) |
| `reasons` | JSON 배열, 이 지역에 추천 수단이 필요한 이유 1~3개 (현행 유지 지역은 지금으로 충분한 이유) |
| `cautions` | JSON 배열, 주의사항 1~3개. 지표 신뢰도가 낮은 지역은 그 문장이 맨 앞 |
| `summary` | 대시보드 미리보기 '추천 근거 요약' 한 줄 (45자 이내). 현행 유지 지역은 "…, 현행 유지" |
| `source`, `created_at` | `llm` / `template`, 만든 시각 (화면의 'LLM 생성' 표시·생성 시각) |
| `context` | LLM에 넘긴 사실. '다시 생성' 때 `prompts/explanation.md`의 `{context}`에 이걸 넣어 다시 부르면 돼요 |

`options` 한 칸:
```json
{"mode": "DRT", "name": "똑버스", "subtitle": "수요응답형 버스", "desc": "정해진 노선 없이 호출에 따라 운행해요",
 "status": "추천", "rank": 1, "score": 86.2, "is_current": false,
 "reasons": ["호출하면 집 가까이 와서 정류장이 먼 마을에 맞아요.", "…"],
 "facts": ["정류장 500m 안에 드는 면적 51% (평균 77%)", "인구밀도 130명/km² (평균 7,364명/km²)"],
 "together": "행복택시: 큰길은 버스가, 마을 안쪽은 택시가 맡아 서로 보완해요."}
```
- `mode`: BUS / DRT / HAPPY_TAXI / KEEP(현행 유지). 현행 유지 카드는 `score`가 null, `is_current`가 false
- `status`: 추천 / 제외. `rank`: 1·2 (제외는 null)
- `reasons`: 그 수단 bullet, **숫자 없이** (숫자는 바로 옆 `facts`에). 추천은 1~2개(왜 맞는지), 제외는 1개(왜 이번엔 덜 맞는지)
- `facts`: '근거 지표' 줄. **서버가 만든 숫자**라 LLM이 숫자를 잘못 옮길 일이 없어요. 추천 최대 3줄, 제외 최대 2줄
- `together`: 추천이 2개일 때 "다른 추천 수단 이름: 둘을 함께 하면 좋은 이유" 한 줄 (LLM이 씀), 아니면 null
- 화면 역할: 카드 bullet = 왜 이 수단인지(숫자 없이) / 근거 지표 = 숫자 / 추천 근거(`reasons`) = 지역 문제를 숫자로. 같은 문장이 반복되지 않게 나눴어요
- 문장 끝 마침표는 서버가 통일해요 (`summary`는 마침표 없이 명사로 끝남)

## 월별 점수
- 입력: `feat_village_month`(리 × 월), `feat_region_month`(행정동 × 월). yong 프로젝트 `03_features.py`가 만들어요.
- **달마다 바뀌는 값:** 1회당 승차(혼잡), 승차·생활인구(잠재 수요), 택시 호출(최근 3개월), 민원(그 달 건수)
- **연간 값 그대로인 것:** 인구·고령 비율, 버스 운행 횟수·대기시간, 도보 시간, 모델 예측. 운행 시간표와 인구가 한 시점 데이터뿐이라서예요.
- 월별 백분위는 12개월을 한꺼번에 매겨요. 달끼리 비교할 수 있어요.
- 생활인구는 공공데이터 원본 그대로 써요. 유림동 2025-10~12처럼 평소와 크게 다른 달(약 6배)도 빼지 않아요 (`fp_anomaly`는 표시만).
- 지역 유형·AI 카드도 달마다 만들어요 (`ml_region`, `ml_explanation`의 `month`). 그 달 점수와 그 달 값(승차·택시·생활인구)으로 만들고, 비교 평균도 그 달 기준이에요.
  - 카드의 택시 근거 지표는 화면 그래프와 같은 숫자가 나오게 그 달 원본 값(`feat_region_month`)을 써요. 점수 계산용 택시 값(최근 3개월)과는 달라요.
  - 지표 신뢰도(표본 부족)도 달마다: 행정동은 그 달 택시 호출이 100건 미만이면 표시돼요.

## 계산 방식
**적합성 평가 (머신러닝)**
- **행복택시**: 리 72개 중 실제 운영 중인 18개를 정답으로 **방향 고정 로지스틱 회귀**. 특성은 70세 이상 비율, 인구, 인구밀도, 접근 정류장 운행 횟수·대기시간, 도보 시간, 500m 안 면적, 거점까지 시간, 5회 이하 정류장 비율이에요.
  각 특성의 방향을 상식대로 묶어요(운행이 적을수록, 고령이 많을수록, 대기·도보가 길수록 행복택시 쪽. 반대 방향이 나오면 그 계수는 0).
  그냥 학습하면 겹치는 특성끼리(대기시간↔운행 횟수, 도보 시간↔500m 안 면적) 부호가 뒤집혀 "대기가 짧을수록 행복택시" 같은 근거가 나왔어요(리 56곳).
  정확도(AUC)는 0.755 → 0.729로 흔들림(±0.021) 안쪽 차이이고, 결과는 오히려 덜 흔들려요(±0.011). 실제로 남는 특성은 5회 이하 정류장 비율, 70세 이상 비율, 인구(작을수록), 운행 횟수(적을수록)예요.
  점수는 교차검증 예측(그 마을을 빼고 학습한 모델)이라 운영 중인 마을도 공정하게 평가돼요.
  여기에 택시(호출 많고 잘 안 잡힘)를 15% 섞어요(`config.TAXI_BLEND`). 모델 안에 넣지 않는 이유: 운영 마을 18개 중 16개가 백암·원삼이라
  면 단위 값을 넣으면 정확도(AUC 0.755 → 0.883)가 오르는 것처럼 보여도 실제로는 "어느 면인지"를 외우는 거예요.
- **똑버스**: 정류장 단위로 "노선버스 1회당 승차"를 예측하는 모델(그래디언트 부스팅)을 써요. 노선버스 예상 효율이 낮을수록, 정류장이 멀고 흩어져 있을수록, 밀도가 낮을수록, 택시 호출이 많고 잘 안 잡힐수록 점수가 높아요(네 가지 같은 비중).
- **노선버스**: 정류장 단위로 "비슷한 조건이면 하루 몇 회 다니는지"를 예측해요. 실제가 예측보다 적을수록, 붐빌수록, 밀도가 높을수록, 출퇴근 시간에 이동이 몰릴수록 점수가 높아요(네 가지 같은 비중).
- **택시**: 인구 1,000명당 호출(시 평균 대비)과 성사율을 같이 봐요. 성사율만 보면 택시 기사 수 문제가 섞여 버스 많은 수지 도심도 나쁘게 나와요.
  월별은 최근 3개월로 계산하고, 앱 이용이 해마다 늘어서 호출 수는 그 달 시 평균 대비로 비교해요.
- **출퇴근 비중**: 평일 7~9시·17~19시 생활인구 / 하루 평균. 정해진 시간에 몰리는 이동은 고정 노선(증차)이 유리해요.
- 택시·출퇴근 비중은 행정동 단위라 리는 그 면의 값을 같이 써요.
- **민원**: 세 수단 모두 마지막에 해당 수단 민원(인구 1,000명당)을 15% 섞어요(`config.COMPLAINT_BLEND`).
- **행정동의 행복택시 점수**: 읍면은 그 안 리 점수를 인구로 가중평균해요. 도시 동은 대상이 아니라 비워 둬요.

**우선순위 평가**: 부적합 정도 = 가장 적합한 수단 점수 − 지금 운영 중인 수단 점수예요. 나머지 항목은 지표 백분위로 0~100이 돼요.
기본 가중치는 30/20/20/10/10/5/5. 처음엔 25/20/20/15/10/5/5 였는데 2025 데이터로 점검해서 바꿨어요. 부적합은 대부분 0 근처라 25를 줘도 실제 영향이 15~18%였고,
취약인구는 서비스 부족·민원과 겹쳐서 15를 줘도 리에서 28%였어요. 가중치를 조금씩 흔들어도 상위 10곳은 82~93% 그대로라 순위는 안정적이에요.

**AI 추천 해결방안 카드**
- **추천/제외는 서버가 정해요.** 적합성 1위 = 추천 1. 2위는 50점 이상이고 1위와 10점 안이면 추천 2, 아니면 제외(`config.RECOMMEND_MIN`, `RECOMMEND_GAP`). 현행 유지 지역은 '현행 유지'가 추천 1이고 세 수단은 모두 제외예요.
- **LLM은 문장만 써요** (`prompts/explanation.md`): 수단별 bullet, 함께 추천된 대안 한 줄, 지역 근거 1~3개, 주의사항, 대시보드 한 줄. 말투는 해요체 (대시보드 한 줄만 명사로 끝남).
- **LLM에는 점수·백분위 대신 사실을 넘겨요.** 수단마다 '유리한 사실 / 불리한 사실'을 실제 값과 평균으로 넘기고, 높다·낮다 방향도 서버가 정해요.
  평균과 10% 안쪽으로 비슷한 값(예: 성사율 53% vs 54%)은 근거로 쓰지 않고 '평균과 비슷'으로 넘겨요 (`config.FACT_MIN_GAP`).
  현행 유지 지역에서 지금 운영 중인 수단은 '그대로 둠'만 넘기고 불리한 사실·근거 지표는 붙이지 않아요.
  비교 평균: 행정동은 용인시 평균(38개 동), 리는 읍면 마을 평균(72개 리), 면 단위 값(택시·출퇴근)은 용인시 평균. 고령 비율·택시 성사율은 그래프와 같은 `feat_city` 값.
  예) `인구밀도 38명/km² (읍면 마을 평균 434명/km²보다 낮음)`
- **숫자가 들어가는 근거 지표 줄(`facts`)은 서버가 만들어요.**
- **서버가 LLM 문장을 검사해요.** 넘기지 않은 숫자, 해요체가 아닌 말투, 점수·순위·백분위·'모델' 같은 말, 추천인데 '제외'처럼 쓴 문장,
  수단 bullet에 숫자, 괄호 없는 비교('평균 54%보다'), 이유 없이 결론만 쓴 제외 문장, '~해요'로 끝난 대시보드 한 줄, 추천 2개인데 together 없음,
  길이(수단 bullet·together 60자, 근거 110자, 주의사항 90자, 한 줄 45자). 걸리면 문제를 알려 주고 다시 쓰게 해요(최대 3번). 그래도 안 되면 같은 모양의 템플릿 문장.
- **주의사항은 서버가 고른 후보에서만** 나와요(똑버스 운영 구역 자료 없음, 면 단위 값, 좌표 없는 정류장, 더미 민원 등). 지표 신뢰도 문장은 서버가 맨 앞에 넣어요.
- 키가 없거나 실패하면 템플릿 문장(`source = template`). 카드 모양은 같아서 화면은 그대로 쓰면 돼요.

## 한계 (발표 때 같이 말하면 좋은 것)
- 행복택시 정답이 18개 마을뿐이라 모델이 단순해요(방향 고정 로지스틱 회귀). 실제로 쓰이는 특성은 4개예요.
- 노선버스 효율·공급 모델의 설명력(R²)은 낮은 편이에요. 순위 비교용이고 정확한 값 예측용은 아니에요.
- 하루 운행 횟수는 배차간격으로 계산한 추정치예요(BMS 실제 기록 아님).
- 민원은 시연용 더미예요(`is_dummy = 1`).
- 똑버스 실제 운영 구역 정보가 없어 "지금 운영 중"에 반영되지 않아요(`feat_*.drt_zone` 채우면 반영).
- 리의 택시·생활인구는 면 단위 값이에요.
